# MBOYO Working Contract

## Mission

Build an offline-first disaster reporting and response coordination platform that lets Reporters submit incidents without connectivity, lets Verifiers make evidence-based human classification decisions assisted (never overridden) by computer vision, lets Response Coordinators dispatch and track operational response against verified incidents, and gives Auditors an immutable, read-only view of the full lineage — from report to model score to human decision to dispatch.

Target: VETERAN KUKUS × Hackathon Bank Indonesia 2026 capstone, Top 80 readiness, with a production-minded architecture and a deterministic live-demo mode.

## Non-Goals

- MBOYO does not replace human judgment in incident verification — ML output is advisory input to the Verifier role, never an autonomous decision-maker.
- MBOYO does not guarantee real-time dispatch of physical resources (vehicles, personnel) — it coordinates and tracks response tasks; execution in the field is out of scope.
- MBOYO does not build a general-purpose CMS, ticketing system, or messaging platform beyond what disaster reporting/response requires.
- MBOYO does not target full production hardening (e.g., multi-region failover, SOC2 compliance tooling) within this capstone scope — it targets a production-*minded* architecture, not a fully hardened production deployment.
- MBOYO does not fabricate or inflate ML performance claims for demo purposes.

## Definition of Done

A block/feature is done when:
- It runs independently and is reviewable as a standalone diff.
- TypeScript strict mode and Python type hints pass with no suppressed errors.
- RBAC boundaries are enforced at the API/RLS layer, not just hidden in the UI.
- Offline-first invariants hold for any Reporter-facing flow touched.
- Any ML-related claim is backed by a measured evaluation on an untouched test set, or is absent.
- Any demo fallback is flagged, visibly labeled, and documented as a limitation.
- Verification (typecheck, lint, tests, build) has been run and results are reported, not assumed.
- Bahasa Indonesia is used for all user-facing copy.
- No secrets, credentials, or raw sensitive evidence are committed.

## Demo-Mode Policy

- Demo mode exists to produce a deterministic, reliable live-demo path when live infrastructure (real ML inference, live GPS, network conditions) cannot be guaranteed during a presentation.
- Demo mode must be explicitly toggled via `DEMO_MODE` / `NEXT_PUBLIC_DEMO_MODE` environment variables — never silently triggered by error states or missing config.
- Every simulated/mocked value shown in demo mode must carry a visible UI label (Bahasa Indonesia) identifying it as simulated/demo data.
- Demo mode must not be the default in any environment other than an explicitly configured demo deployment.
- Demo mode fallbacks must be enumerated in the block summary that introduces them.

## Production-Mode Policy

- Production mode uses live Supabase auth/RLS, live ML inference through `apps/ml-api`, and real offline sync via Dexie + Background Sync.
- No mocked responses, canned confidence scores, or simulated network conditions are permitted in production mode.
- All role-gated actions are enforced server-side (API route + RLS), with UI-level restrictions treated as UX convenience only, never as the security boundary.
- Secrets required for production (service-role key, ML internal token, VAPID keys, signing secrets) are never exposed client-side.

## Never-Fake Checklist

Before marking any block complete, confirm:
- [ ] No ML metric (accuracy, precision, recall, F1, confidence) is invented, guessed, or copied from an unrelated run.
- [ ] No API response is hardcoded/mocked outside of an explicitly labeled demo-mode path.
- [ ] No test is asserting against a fake/stubbed result presented as if it exercised real logic, unless the test explicitly declares it's testing a mock.
- [ ] No error is silently swallowed or hidden behind a disabled lint rule or `any` cast.
- [ ] No UI element claims real-time/live data when it is actually static or cached beyond a reasonable staleness window without disclosure.
- [ ] No secret, credential, or raw evidence file is staged for commit.
